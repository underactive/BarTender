# Research: screen-lock

## Research Question
Add a user-initiated screen lock to the device. Locking starts with a swipe down gesture, keeps the stats view updating, suppresses screensaver entry while locked, and unlocks only with a swipe up gesture; after unlock, the screensaver countdown resumes immediately.

## Summary
The lock feature fits into the existing semantic-event UI pipeline: touch emits APP_EVT_* gestures, ui.c owns nav/input state, ui_screensaver.c owns saver timing, and ui_render.c owns both summary and card chrome. The cleanest integration is a separate shared `locked` bit in `st`, with swipe-down entering lock, swipe-up exiting it, and idle entry blocked only while locked. Rendering can stay live because `ui_task()` continues to merge stats, mark dirty, and call `render()` regardless of lock state.

## Detailed Findings

### UI state and saver lifecycle
- `ui_internal.h:136-172` already centralizes all shared UI state in `st`; `saver_active`, saved-nav fields, and `last_input_ms` are adjacent, but there is no existing lock slot.
- `ui.c:123-149` drives saver entry from `st.last_input_ms` and `SCREENSAVER_IDLE_MS`, then runs `saver_advance_locked()` and `render()` on the same loop.
- `ui_screensaver.c:169-255` snapshots/restores nav state only for saver mode; `saver_exit_locked()` restores `nav_level`, `nav_provider`, `nav_id`, `nav_card`, and `scroll`.
- The discover decision to keep lock separate aligns with this split: lock should gate saver entry, not overload saver state.

### Gesture pipeline
- `app_event.h:11-20` defines the only gesture events available to UI logic: TAP, SWIPE_UP, SWIPE_DOWN, SWIPE_LEFT, and LONG_PRESS.
- `touch.c:70-164` classifies raw touch into exactly one semantic event per press; swipe direction is already available at the UI layer.
- `ui.c:251-309` is the sole nav/input state machine. Summary scroll, page open/toggle, and back-nav already live here, so lock/unlock should also be handled here rather than in touch.
- Since swipe-down currently scrolls the summary list (`ui.c:271-278`), lock entry needs a nav-aware branch to avoid clashing with list paging.

### Screensaver suppression and unlock timing
- `ui.c:123-130` is the only automatic saver entry gate: when idle expires and `st.saver_active` is false, it calls `saver_enter_locked(now)`.
- `ui_handle_input()` currently sets `st.last_input_ms` on every input and exits saver immediately if `st.saver_active` is set (`ui.c:259-263`), which is the right hook for unlock, but not enough to block saver entry while locked.
- `saver_enter_locked()` in `ui_screensaver.c:169-187` is the place to add a lock guard; `saver_exit_locked()` in `ui_screensaver.c:251-255` already restores prior nav state and re-fades to configured brightness.
- The unlock gesture should refresh `last_input_ms` so the existing idle timer restarts immediately after unlock.

### Header chrome and lock icon placement
- `ui_render.c:494-541` is the shared page-chrome helper used by both cost and limits cards; it already owns the top-left title/icon layout on provider pages.
- `ui_render.c:1042-1109` and `ui_render.c:1190-1193` both pass page chrome through that helper, so a lock badge added there reaches both card types.
- Summary chrome is separate: `ui_render.c:1451-1529` owns the summary footer/status band, while `ui_render.c:1533-1560` controls the top summary hero block.
- Because the FRD requires the icon on both summary and provider pages, the indicator likely needs a shared chrome helper plus a summary-path overlay or badge in the footer/top band.

### Live refresh behavior
- `ui_set_stats()` in `ui.c:198-225` always copies stats, updates activity, sets `fetched_ms`, and marks dirty; it does not depend on saver state.
- `ui_task()` in `ui.c:123-149` keeps calling `render()` whenever dirty, and `render()` recomputes age text from `st.fetched_ms` on demand (`ui_render.c:1518-1526`).
- `ui_render.c:1484-1543` shows the summary footer and age suffix are rebuilt from current shared state every render, so locking should not freeze freshness text or provider values.
- The only risk is accidental coupling to `saver_active` in render gating; current code avoids that for the summary path.

## Architecture Insights
- The codebase already follows the right separation for lock: gesture classification in touch, policy in ui.c, saver mechanics in ui_screensaver.c, chrome in ui_render.c.
- A new lock bit should stay independent of saver state so saver restore remains trustworthy.
- Lock should suppress saver entry only; it should not suppress stats ingestion or render invalidation.
- `render_page_chrome()` is the best reuse point for a provider-page lock badge, but summary needs a separate badge path because its chrome is not built through that helper.
