# Research: Pi Agent stats

## Research Question
How should Pi Agent be added as a first-class provider in the existing v2 payload while preserving the current provider model, privacy-reduced contract, and firmware rendering path?

## Summary
The host pipeline is split into two clear seams: `scripts/codexbar-stats.sh` handles live CodexBar provider discovery and projection, while `scripts/codexbar-publish.sh` handles fail-safe local-file augmentation before publishing. Firmware already accepts arbitrary provider IDs, preserves provider array order, and renders provider-specific visuals through lookup tables rather than special-case branches. Pi is already wired into the icon/color path, so the remaining work is mainly a new Pi source helper on the host side plus a payload merge path that preserves the existing reduced contract.

The developer checkpoint selected a **separate helper** for Pi local-source parsing and reduction, which fits the current architecture best: keep the live collector unchanged, and invoke a Pi-specific helper from the publisher/augmentation side.

## Detailed Findings

### Host collection and publish seams
- `scripts/codexbar-stats.sh:83-93` discovers enabled provider IDs from CodexBar config and turns them into the provider list used for live fetches; there is no standalone provider registry.
- `scripts/codexbar-stats.sh:132-208` reduces each live provider result into the compact `providers[]` JSON shape for v2 output.
- `scripts/codexbar-publish.sh:100-106,228-375` is the existing fail-safe augmentation boundary: it already reads local cache/history data, merges derived fields, and skips on cache/schema failure rather than blanking remote state.
- Developer decision: Pi source parsing and reduction should live in a **separate helper** invoked from the publisher-side augmentation path, not in the live collector.

### Payload contract and parser
- `docs/generated/codexbar-payload.schema.json:5-56` defines the inner v1/v2 contract; v2 is a strict superset of the same provider-array shape.
- `firmware/main/stats_model.h:18-56` already has the flat provider struct needed for a provider row, trailing 30-day spend, trailing 30-day tokens, per-day spend history, and optional 24h usage-percent history.
- `firmware/main/stats_model.c:33-136` parses the Upstash envelope and inner payload in two steps, accepts v1 or v2 only, and preserves unknown provider IDs without whitelisting.
- `firmware/main/stats_model.c:71-136` appends providers in payload order and leaves missing optional fields unset, which is exactly what a first-class Pi row needs if its data is partial.

### Firmware rendering path
- `firmware/main/ui.c:991-1005` re-resolves the selected provider by ID after refresh, so provider identity is stable even if the array order changes.
- `firmware/main/ui.c:1017-1096` renders summary rows directly from `stats_t.p[]`, using provider IDs for labels, icons, and accent colors.
- `firmware/main/ui.c:757-959` renders the provider cards from the flat stats model fields; the card logic is data-driven, not provider-specific.
- `firmware/main/provider_icons.c:1154-1192` and `firmware/main/provider_colors.h:14-49` are explicit lookup tables, not generic catch-alls; unknown IDs simply fall back to no icon or neutral styling.

### Provider branding and generation
- `scripts/gen-provider-icons.py:1-125` is the generator that rasterizes SVG assets into `firmware/main/provider_icons.c` and `.h`.
- `scripts/gen-provider-icons.py:26-40` contains the provider-id to SVG mapping, including `pi -> pi`.
- `firmware/main/provider_icons.c:990-1028` already contains the Pi icon asset, and `firmware/main/provider_icons.c:1183-1185` already maps provider ID `pi` to that asset.
- `firmware/main/provider_colors.h:16-18` already assigns Pi a brand color, so Pi can render through the same card/header styling path as existing providers.

### Privacy and failure behavior
- `docs/SECURITY.md:20-46` documents the relaxed single-user channel: the reduced payload is intentionally allowed to carry real spend data, but the host still must not leak raw upstream details.
- `scripts/codexbar-stats.sh:162-208` keeps live-provider reduction focused on usage windows and reduced cost fields only; it structurally avoids identity fields.
- `scripts/codexbar-publish.sh:252-375` enforces fail-soft local augmentation: cache mismatch or absence skips the merge and still allows publishing usage-only data.
- The current codebase does not reference `~/.pi/agent` anywhere in the host pipeline, so Pi Agent data is not currently conflated with CodexBar's `pi-sessions` cache path.

## Architecture Insights
- The host collector is the canonical source of provider ordering; firmware preserves whatever order it receives instead of inventing its own.
- Reduction belongs on the host, not in firmware; firmware is a parser/renderer for already-reduced data.
- Provider presentation is explicit and lookup-driven: icons and colors are decoration tables, not a generic renderer.
- Unknown provider IDs are acceptable in the payload model; they only lose branded presentation if no icon/color lookup exists.
- Pi is already first-class in the branding pipeline, so the missing piece is host-side source discovery and reduction, not firmware identity plumbing.

### Composite Lessons
- Add the provider to the shared v2 payload first, then verify firmware formatting/layout on tiny values and non-cost providers.
- Treat host-side merging as a failure-prone edge: missing or partial local data should fail soft, and provider-specific date guards can overblock when generalized.
- Keep Pi data sources separate from CodexBar cache names: `pi-sessions` is unrelated to Pi Agent and should not be mixed into collection logic.
