# FRD: LM Studio stats on device

## Summary
Add a new `lmstudio` provider to the BarTender payload pipeline that surfaces local LM Studio inference metrics — requests, tokens, model popularity, and cache utilization — from the server logs at `~/.lmstudio/server-logs/`. The firmware gains four custom pages (TODAY, STATS 1, STATS 2, STATS 3) with dual progress bars on the summary and a purple accent, all following the existing card system navigation pattern.

## Problem & Intent
Eric wants to see his local LM Studio usage metrics alongside CodexBar stats on the single desk toy display — one glance shows both AI provider usage and local inference activity. This is about unified personal telemetry: the device becomes a single physical dashboard for all his AI tooling, both cloud (CodexBar providers) and local (LM Studio inference).

## Goals
- Parse `~/.lmstudio/server-logs/` logs to extract daily requests, tokens, cache utilization, and model usage
- Publish LM Studio metrics to Upstash as a new provider entry in the existing payload
- Show two progress bars on the summary page (Tokens bar + Requests bar) under the Pi entry, using the LM Studio purple accent
- Provide 4 custom detail pages: TODAY (hero tokens, hero requests, 30-day bar chart, 30-day max), STATS 1 (tokens %, requests %), STATS 2 (top 10 models table), and STATS 3 (7-day daily usage table)
- Store a rolling 30-day history of daily requests and tokens for max-value comparison bar charts
- Only surface daily-aggregate stats — no per-request data, no raw prompt content

## Non-Goals
- No cost / spend tracking for LM Studio (it's free/local). No money widgets, hero amounts, or extra usage bars.
- History storage is host-side only. The rolling history file lives on the Mac, not on the device. The firmware receives pre-computed daily values.
- No real-time log watching. The host script parses logs once per publish cycle (every 5 min). No fsnotify/kqueue.
- No per-model drill-down pages. The top-10 table on STATS 2 is terminal — no tapping a model for more detail.
- No model-level detail pages beyond the top-10 breakdown.
- No configuration UI on the device for LM Studio settings.

## Functional Requirements
1. The host script SHALL parse `~/.lmstudio/server-logs/2026-MM/YYYY-MM-DD.*.log` files to extract the day's /v1/chat/completions request count and total tokens from `slot release` `n_tokens` values.
2. The host script SHALL compute cache % (KV cache MiB usage / MiB limit) from `cache state:` lines.
3. The host script SHALL compute cache hit % (average of `cached_tokens / total_tokens`) from `[cache_wrapper] Prompt cache: using X/Y tokens from cache` lines.
4. The host script SHALL extract the model name from each `/v1/chat/completions` request body's `"model"` field for the top-10 model breakdown.
5. The host script SHALL discover which model is currently loaded by scanning the most recent `[INFO][LM STUDIO SERVER]` startup lines or the model field in recent request bodies.
6. The host script SHALL read the rolling history file at `~/.config/codexbar-toy/lmstudio-history.json` to compute 30-day max tokens and max requests, appending today's data on each publish cycle.
7. The host script SHALL produce a JSON payload with an `lmstudio` provider entry containing an `lm` sub-object with today's stats, percentages, top-10 model list, and 7-day daily table.
8. The publisher SHALL integrate `lmstudio-stats.sh` into the `codexbar-publish.sh` pipeline as a new stage (similar to the Pi agent merge), publishing to Upstash in the same payload.
9. The firmware SHALL render the `lmstudio` provider row on the summary page with a single row showing two stacked bars: a larger Tokens bar and a thinner Requests bar, colored in the LM Studio purple accent.
10. The firmware SHALL implement 4 custom pages for LM Studio navigated by tapping: TODAY (Cost card slot) → STATS 1 (Limits card slot) → STATS 2 → STATS 3 → back to TODAY, cycling through all 4 pages.
11. The firmware SHALL render the TODAY page with: a hero token count (font_lemonmilk_48), a smaller hero request count, a 30-day token bar chart, and 30-day max tokens + 30-day max requests labels at the bottom.
12. The firmware SHALL render the STATS 1 page with: a hero tokens % (same % from summary bar, like "Session %" style), and a sub-hero requests % (like "Weekly %" style).
13. The firmware SHALL render the STATS 2 page with a top-10 models table (Rank, Model name, Request count).
14. The firmware SHALL render the STATS 3 page with a 7-day table (Date, Requests, Tokens, Cache %, Cache Hit %).

## Non-Functional Requirements
- **Performance**: The host script must complete within 10s (log parsing of up to ~50 log files per day, each up to ~10MB). The firmware pages must render within the existing 5ms tick cycle.
- **Security**: No raw prompt content, model paths, or API keys leave the Mac. Only aggregated counts and percentages are published. The rolling history file is local to `~/.config/codexbar-toy/` — not committed to git.
- **UX**: Pages follow the existing visual language — purple accent for LM Studio, same fonts, same progress bar styles. Touch gestures (tap/swipe) behave identically to other provider pages.
- **Reliability**: If the LM Studio server is not running or log files are unavailable, the `ok` flag is false and the device gracefully hides LM Studio. Rolling history is pruned to 30 days. Cache metrics gracefully fall back to 'N/A' when cache_wrapper data is absent (e.g., GGUF backend vs MLX backend).
- **Data model**: All LM Studio-specific fields live in an `lm` sub-object on the provider entry (like `pi` for Pi Agent), keeping the cost/usage fields clean.

## Constraints & Assumptions
- LM Studio logs are at `~/.lmstudio/server-logs/2026-MM/YYYY-MM-DD.*.log` (confirmed on Mac — monthly subdirectories, daily files with `.N.log` suffixes for rotation).
- Log format is `[YYYY-MM-DD HH:MM:SS][LEVEL][...]` with specific markers for chat completions (`Received request: POST to /v1/chat/completions`), slot releases (`slot release: ... stop processing: n_tokens = N`), cache state (`cache state: N prompts, X MiB (limits: Y MiB)`), and cache wrapper hits (`Prompt cache: using X/Y tokens from cache`).
- The rolling history file lives at `~/.config/codexbar-toy/lmstudio-history.json` — same config directory as the existing codexbar-toy publish config.
- LM Studio stats script runs every 5 minutes (same publish cycle as existing CodexBar pipeline).
- Firmware reuses the ESP-IDF LVGL display system with LV_CHART_TYPE_BAR for the TODAY 30-day chart and the LVGL table widget for STATS 2 and STATS 3.
- The existing `provider_colors.h` already maps `"lmstudio"` to `0x7C3AED` (purple) — no color change needed.
- The firmware nav system extends the existing card cycle: CARD_COST → CARD_LIMITS → CARD_LM_STATS_2 → CARD_LM_STATS_3 → back to CARD_COST for LM Studio provider only.

## Acceptance Criteria
- [ ] Running `./scripts/lmstudio-stats.sh` prints a JSON payload with `id: "lmstudio"`, `ok: true/false`, and an `lm` sub-object containing today's requests, tokens, percentages, history, and model breakdown
- [ ] The rolling history file at `~/.config/codexbar-toy/lmstudio-history.json` is read and updated correctly, pruned to 30 entries
- [ ] The top-10 models table shows models sorted by request count descending, with Rank, Model name, and Request count columns
- [ ] The 7-day daily usage table includes Date, Requests, Tokens, Cache %, and Cache Hit % columns
- [ ] The firmware summary page shows an LM Studio row with a dual stacked bar (Tokens + Requests) under Pi, with a purple accent
- [ ] Tapping the LM Studio row opens TODAY page first, then cycles through STATS 1 → STATS 2 → STATS 3 → back to TODAY on each tap
- [ ] Cache % and Cache Hit % gracefully show 'N/A' when the backend doesn't report cache_wrapper data
- [ ] When LM Studio is not running (no logs found), `ok: false` and the device shows the provider as offline/dimmed
- [ ] The publish pipeline (`codexbar-publish.sh --once`) includes `lmstudio-stats.sh` output in the final payload sent to Upstash

## Recommended Approach
A standalone Python3 script `scripts/lmstudio-stats.sh` (with a shebang and inline Python, mirroring `pi-agent-stats.sh`) that parses today's log files, reads/updates the rolling history file at `~/.config/codexbar-toy/lmstudio-history.json`, and outputs JSON to stdout. The existing `codexbar-publish.sh` gains a new merge stage that runs `lmstudio-stats.sh` and injects the result as an `lmstudio` provider with an `lm` sub-object. The firmware adds an `is_lm` flag in `render_card()` to trigger custom rendering for TODAY/STATS 1/STATS 2/STATS 3 pages, accumulating new card types beyond CARD_COST/CARD_LIMITS.

## Decisions

### Scope — all components in
**Question**: Which of these firmware pages and host components should be in scope?
**Recommended**: All 7 components (Summary progress bars, TODAY page, STATS 1, STATS 2, STATS 3, host script, 30-day history)
**Chosen**: All 7
**Rationale**: The user confirmed every component from the original spec is in scope.

### LM Studio color — keep purple #7C3AED
**Question**: LM Studio already has purple (#7C3AED) registered in provider_colors.h. Keep it, or change?
**Recommended**: Keep purple #7C3AED
**Chosen**: Purple #7C3AED
**Rationale**: evidence: firmware/main/provider_colors.h:39 — already registered, no change needed.

### Data carrier — reuse providers[] array
**Question**: Should LM Studio data go in a separate top-level payload section, or inside the existing providers[] array?
**Recommended**: Reuse providers[] array
**Chosen**: Reuse providers[] array
**Rationale**: Consistent with how Pi is handled — LM Studio appears as another provider entry in the existing array. Simpler parsing on the firmware side.

### History storage — single rolling file
**Question**: How should we store the 30-day rolling history needed for max-value comparison and bar charts?
**Recommended**: Single rolling history file at ~/.config/codexbar-toy/lmstudio-history.json
**Chosen**: Single rolling history file
**Rationale**: Same config directory as existing publish config, single file to manage, updated each publish cycle, pruned to 30 days.

### Non-goals — what's out of scope
**Question**: Which should be explicitly OUT of scope?
**Recommended**: No cost/spend tracking, History is host-side only, No real-time log watching, No per-model drill-down
**Chosen**: All four confirmed out
**Rationale**: Keeps scope focused on the core display features; reduces firmware complexity and host-side resource use.

### Cache metrics — compute from logs
**Question**: How should Cache % and Cache Hit % be handled in the 7-day table?
**Recommended**: Compute from log data with graceful 'N/A' fallback
**Chosen**: Compute from log data
**Rationale**: Cache % is parseable from `cache state:` lines (current MiB / limit MiB). Cache Hit % is the average of `cached_tokens / total_tokens` from `[cache_wrapper]` lines. Graceful fallback when the backend doesn't report cache_wrapper data (e.g., GGUF vs MLX).

### Payload shape — `lm` sub-object
**Question**: How should LM Studio-specific data be structured inside the provider entry?
**Recommended**: `lm` sub-object on the provider (like Pi's `pi`)
**Chosen**: `lm` sub-object
**Rationale**: Clean separation from the cost/usage fields. Mirrors the existing `pi` sub-object pattern. All LM-specific fields (requests, tokens, history, percentages, model breakdowns, 7-day table) live in one place.

### Pyaload fields — what the `lm` sub-object contains
**Question**: Which data fields should the LM Studio payload include?
**Recommended**: All requested fields
**Chosen**: Requests today, Tokens today, 30-day max + daily history (tokens), 30-day max + daily history (requests), Tokens % vs max, Requests % vs max, Top 10 models breakdown, 7-day daily table data
**Rationale**: Core LM Studio metrics — requests and tokens — drive the progress bars and TODAY page. The aggregated fields (percentages, top models, 7-day table) power STATS pages 1-3. Cache % and Cache Hit % are included in the 7-day daily table rows.

### Navigation — extend existing card system
**Question**: How should the 4 LM Studio pages be organized in the navigation?
**Recommended**: Extend existing card system — TODAY in Cost card slot, STATS 1 in Limits card slot, tap again for STATS 2, tap again for STATS 3, then wrap back to TODAY
**Chosen**: Extend existing card system
**Rationale**: Fits the existing tap-to-cycle pattern that users already know. No new navigation paradigm needed. Requires adding 2 new card type enum values (CARD_LM_STATS_2, CARD_LM_STATS_3).

### Summary bars — single row dual stacked bars
**Question**: How should the Tokens and Requests progress bars appear on the summary?
**Recommended**: Single row with dual stacked bars
**Chosen**: Single row with dual stacked bars
**Rationale**: Mirrors the existing Claude/Codex pattern of session bar + weekly bar stacked vertically in one row. A larger bar for tokens and a thinner bar for requests, both purple.

### Script language — Python3
**Question**: What language should the lmstudio-stats.sh host script use?
**Recommended**: Python3 script (inline Python with bash wrapper, same pattern as pi-agent-stats.sh)
**Chosen**: Python3
**Rationale**: Log file parsing with regex, datetime arithmetic, and JSON generation are significantly easier and more maintainable in Python than zsh/JXA. The existing pi-agent-stats.sh establishes this precedent.
