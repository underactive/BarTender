# FRD: Pi Agent stats

## Summary
Add Pi Agent to BarTender as a first-class provider source alongside existing stats, so the device can show Pi usage on the screen. The feature should support Pi-specific 30-day max spend and max token summaries, plus a 30-day usage graph.

## Problem & Intent
I want to add Pi Agent (CLI harness) to the BarTender device. CodexBar doesn’t know about Pi, so we need a separate Pi stats path that can read local Pi data and show it on the device. I also want feature parity with CodexBar for Pi-only stats, including 30-day max spend, 30-day max tokens, and a 30-day graph.

## Goals
- Show Pi usage on the BarTender device as a new provider row.
- Track Pi 30-day max spend and 30-day max tokens.
- Render a 30-day Pi usage graph.
- Support Pi data from local CLI output and local files under `~/.pi/agent`.
- Include all usable Pi sources, including LM Studio and OpenRouter.

## Non-Goals
- Do not change CodexBar behavior except where the shared payload contract needs a Pi provider entry.
- Do not publish raw Pi data that would expand the remote payload beyond the reduced stats contract.
- Do not treat Hugging Face as excluded if usable data exists; it stays in scope for discovery.

## Functional Requirements
1. The host-side pipeline SHALL collect Pi stats from Pi CLI output and local state under `~/.pi/agent`.
2. The host-side pipeline SHALL publish Pi as a distinct provider entry in the existing stats payload.
3. The Pi provider entry SHALL include enough fields for the device to render usage limits, 30-day max spend, 30-day max tokens, and a 30-day usage graph.
4. The device SHALL render Pi using the existing provider-based UI model rather than a separate screen path.
5. The published payload SHALL preserve the current privacy reduction rules and omit raw upstream Pi details.

## Non-Functional Requirements
- **Performance**: No specific latency target yet; the new Pi collection path should not noticeably slow the existing publish cycle.
- **Security**: Keep tokens/credentials local; do not commit secrets or publish raw provider data.
- **UX / Accessibility**: Pi should feel like a first-class provider on the device, with the same summary/graph style as the existing provider views.
- **Reliability**: Missing or partial Pi data should fail soft and not block publishing of other stats.

## Constraints & Assumptions
- The current firmware already accepts provider-based stats and 30-day history fields.
- Pi data may come from multiple backends, including local requests via LM Studio and OpenRouter.
- Hugging Face may or may not have usable session data; discovery should confirm what is actually available.
- The work spans both host scripts and firmware rendering.
- **Naming note: CodexBar has a cost-cache file/dataset called `pi-sessions` (e.g. `pi-sessions-v*.json`) which is completely unrelated to Pi Agent (CLI harness). Do not conflate the two. Pi Agent data lives under `~/.pi/agent/`, not in CodexBar's cost cache.**

## Acceptance Criteria
- [ ] Running the publisher with Pi data available results in a payload that includes a Pi provider entry.
- [ ] The device displays Pi with 30-day max spend and 30-day max token summaries.
- [ ] The device displays a 30-day Pi usage graph when history is present.
- [ ] Missing Pi data does not break publishing or rendering for other providers.

## Recommended Approach
Add Pi as a new provider in the existing v2 payload and extend the host-side collector/merger to read Pi’s local CLI/state data. Reuse the current firmware provider model and card rendering so Pi appears as a first-class provider with the same summary and chart patterns.

## Decisions

### Provider shape
**Question**: From the probe I inferred that Pi can be added as a new provider in the existing v2 payload, and the firmware already renders arbitrary provider IDs and 30-day charts from provider fields. Keep that shape, or switch to a different integration shape?
**Recommended**: New provider row (Recommended)
**Chosen**: New provider row
**Rationale**: Reuse the existing provider model and keep Pi first-class without adding a separate screen path.

### Pi sources
**Question**: For Pi stats, which data sources should we include in v1?
**Recommended**: LM Studio + OpenRouter (Recommended)
**Chosen**: All possible Pi Agent backends
**Rationale**: The feature should include every usable Pi Agent (CLI harness) source, not just the two explicitly named ones. This includes backends reachable through `~/.pi/agent/` CLI output and local state. **Note: CodexBar's `pi-sessions` cost-cache files are excluded — they are CodexBar-specific and unrelated to Pi Agent data.**

### Pi metrics
**Question**: Which Pi metrics should the device show in v1?
**Recommended**: Maxes + graph (Recommended)
**Chosen**: Maxes + graph
**Rationale**: This matches the requested parity: 30-day max spend, 30-day max tokens, and a usage trend chart.

### Pi source path
**Question**: Where should the host gather Pi data from?
**Recommended**: CLI + local files (Recommended)
**Chosen**: CLI + local files
**Rationale**: That gives the best chance of covering live usage plus history/max calculations.

None.
