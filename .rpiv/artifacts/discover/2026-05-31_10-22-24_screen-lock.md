# FRD: screen-lock

## Summary
Add a user-initiated screen lock to the device. Locking starts with a swipe down gesture, keeps the stats view updating, suppresses screensaver entry while locked, and unlocks only with a swipe up gesture; after unlock, the screensaver countdown resumes immediately.

## Problem & Intent
I want to add a new feature to lock the screen, preventing the screensaver from starting. When locked the screen still updates stats. When locked, there will be a lock icon in the upper right area (in the header chrome) of the display. Locking starts with a swipe down gesture. The only interaction allowed when locked is a swipe up which unlocks the screen. Right after unlocking, the screensaver countdown timer begins.

## Goals
- Let the user explicitly lock the display with a swipe down gesture.
- Keep stats rendering/updating while locked.
- Prevent the screensaver from starting while locked.
- Show a lock indicator in the header chrome when locked.
- Unlock only via swipe up, then restart the idle countdown immediately.

## Non-Goals
- Adding passcodes, PINs, or any authentication.
- Changing the existing stats data model or payload shape.
- Reworking the current screensaver visuals beyond lock behavior.

## Functional Requirements
1. The firmware SHALL enter a locked state on swipe down from the active stats UI.
2. While locked, the firmware SHALL continue rendering fresh stats updates.
3. While locked, the firmware SHALL not enter the screensaver due to idle timeout.
4. While locked, the firmware SHALL ignore all interactions except swipe up.
5. A swipe up while locked SHALL unlock the screen and restore the prior view.
6. After unlock, the firmware SHALL begin the screensaver countdown immediately from that moment.
7. The firmware SHALL display a lock icon in the upper-right header chrome whenever the screen is locked.
8. The lock icon SHALL appear on both the summary screen and provider pages.

## Non-Functional Requirements
- **Performance**: Locking must not stop or noticeably delay the existing stats refresh/render loop.
- **Security**: No secret material or authentication flow is introduced.
- **UX / Accessibility**: Locked mode must have one clear exit gesture (swipe up) and visible lock state.
- **Reliability**: Unlocking must restore normal idle behavior without leaving the UI stuck in saver state.

## Constraints & Assumptions
- Implement within the existing `firmware/main/` UI, touch, and screensaver split.
- Reuse the current semantic gesture events; do not add raw touch handling elsewhere.
- Assume the lock is purely local and session-scoped, not persisted across reboot.

## Acceptance Criteria
- [ ] Swiping down on the running device visibly enters locked mode and shows a lock icon.
- [ ] While locked, the visible stats continue to refresh after new data arrives.
- [ ] Waiting past the idle timeout while locked does not start the screensaver.
- [ ] Any locked-state gesture other than swipe up is ignored.
- [ ] Swiping up exits locked mode and the idle countdown restarts immediately.

## Recommended Approach
Add a lock flag to the existing UI state and intercept gestures in `firmware/main/ui.c`, while reusing the current render loop so stats continue updating. Extend `firmware/main/ui_render.c` to draw a lock indicator in the shared header chrome and gate saver entry in `firmware/main/ui.c` / `ui_screensaver.c` so lock mode suppresses idle activation.

## Decisions

### Lock behavior
**Question**: From the probe I inferred that locking should keep stats refreshing, block screensaver entry while locked, and make swipe up the only unlock gesture. Keep that behavior, or change it as part of the feature?
**Recommended**: Keep inferred
**Chosen**: Keep inferred
**Rationale**: Matches the requested behavior and existing gesture/saver split.

### Lock icon placement
**Question**: Should the lock icon appear in the header chrome on the summary screen only, or on both summary and provider pages?
**Recommended**: All screens
**Chosen**: All screens
**Rationale**: Keeps locked state visible anywhere the header chrome is present.
