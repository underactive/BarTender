# Design: Pi Agent stats

## Summary
Add Pi Agent as a first-class provider in the existing provider-row payload and render path by introducing a dedicated host-side helper that merges a new `pi` block into the payload before publish. The firmware keeps the same provider model and navigation structure, but learns to render Pi’s max spend, max tokens, and 30-day graph with Pi-specific labels while reusing the existing branded row/icon/color presentation.

## Requirements
- Add Pi Agent as a new provider row in the existing v2 payload.
- Collect Pi stats from local Pi Agent data on the Mac, including CLI/session state under `~/.pi/agent`.
- Preserve the current privacy-reduced contract: only rolled-up stats cross the boundary.
- Keep Pi as a first-class provider in the shared UI model; no separate screen path.
- Render Pi’s max spend, max tokens, and 30-day graph on the device.
- Keep the current provider row / navigation behavior for all non-Pi providers.
- Keep the publish path fail-soft: missing or malformed Pi data must not blank the store.
- Update repo-facing docs so the new provider and local data source are discoverable.

## Current State Analysis
The host pipeline already has a clear split: `scripts/codexbar-stats.sh` produces the base provider usage JSON, and `scripts/codexbar-publish.sh` is the fail-soft augmentation boundary that merges local cache data before POSTing to Upstash. The firmware parser already accepts arbitrary provider IDs and preserves provider-array order, and the renderer is data-driven enough to branch per provider without changing the overall navigation model.

### Key Discoveries
- `scripts/codexbar-publish.sh:228-390` already has the local augmentation seam and the fail-soft publish behavior we should extend.
- `docs/generated/codexbar-payload.schema.json:5-56` is the contract for the inner payload and needs to describe the new Pi provider block.
- `firmware/main/stats_model.h:25-56` already models a provider row with optional provider-specific data blocks.
- `firmware/main/stats_model.c:71-136` parses provider objects permissively and can absorb a new optional block without changing the envelope parse.
- `firmware/main/ui.c:757-843` is the Cost-page branch point where provider-specific labels and chart data can diverge.
- `firmware/main/provider_colors.h:14-49` and `firmware/main/provider_icons.c:1154-1192` already include Pi branding, so no new branding assets are needed.
- `README.md:61-88`, `docs/product-specs/esp32-toy.md:28-44`, and `docs/product-specs/claude-cost-menu.md:30-57` are the user-facing descriptions that need to be brought in sync.
- `docs/EXTERNAL_INTEGRATIONS.md:8-50` documents the existing host→cloud→device path and should mention the new Pi local-source integration.
- Pi’s documented local state lives under `~/.pi/agent/sessions/` and custom model/provider config lives under `~/.pi/agent/models.json`; session files are JSONL trees with `usage` objects that expose tokens/cost per assistant message.

## Scope
### Building
- A standalone Pi helper script under `scripts/`.
- Publisher-side merge wiring for the Pi helper.
- Schema extension for a new optional `pi` provider block.
- Firmware parse/model support for the Pi block.
- Firmware rendering updates for Pi-specific max spend, max tokens, and graph labels.
- User-facing documentation updates in the README, product specs, and integration docs.

### Not Building
- A new Pi-only screen or navigation path.
- Raw Pi session data or per-message detail on the device.
- Any change to Pi branding assets; those already exist.
- Any change to Upstash auth or the read/write token model.
- Any change to CodexBar’s existing provider collection logic.
- Any rewrite of the existing provider-row rendering model for non-Pi providers.

## Decisions
### Provider shape
Keep Pi as a normal provider row in the existing v2 payload and render it through the same provider list / page navigation model. This matches `firmware/main/stats_model.h:25-56` and `firmware/main/ui.c:757-843`, which already accept provider-array growth and provider-specific render branches.

### Metric shape
Use a new optional `pi` sub-object rather than overloading the existing `cost` block. That keeps Pi’s max spend, max tokens, and history semantics explicit instead of pretending they are “today/month” cost metrics.

### Host seam
Keep Pi collection in a separate helper script and have `scripts/codexbar-publish.sh` invoke it during augmentation. That preserves the current publisher-as-fail-soft-boundary pattern already established at `scripts/codexbar-publish.sh:228-390`.

### Local source boundary
Read Pi Agent state from `~/.pi/agent/sessions/` and `~/.pi/agent/models.json`, then reduce it to rolled-up numbers before publish. That aligns with the Pi docs’ JSONL session storage model and keeps raw session trees off the wire.

### UI rendering
Render Pi as a provider-specific Cost-page branch inside the existing provider page chrome, with Pi-specific labels for max spend / max tokens and a 30-day graph. Leave the summary row and the generic provider navigation model intact.

## Desired End State
The host can publish a payload that includes a Pi provider entry alongside existing providers:

```json
{
  "id": "pi",
  "ok": true,
  "p": 41.2,
  "pi": {
    "ps": 1245,
    "pt": 893421,
    "h": [91, 77, 124, 0, 0]
  }
}
```

On the device, the summary row still shows Pi in the same list as the other providers. Tapping Pi opens a Pi-branded Cost page that shows its max spend, max tokens, and 30-day graph, while the rest of the provider navigation continues to work exactly as it does today.

## Ordering Constraints
- The host helper and payload schema must land before the firmware parser changes that consume the new `pi` block.
- The firmware parser/model must land before the UI branch that reads the new Pi fields.
- The UI branch should be reviewed after the parser/model so the render logic can rely on stable field names.
- Docs should be last so they describe the final shape, not a draft contract.
- The host publish path and firmware parser can be implemented and verified before the README/spec edits if needed, but the final artifact should only be completed once the docs match the code.

## Verification Notes
- `scripts/codexbar-publish.sh` must continue to skip publishing when Pi data is absent or unreadable; that fail-soft behavior is intentional.
- The new helper should only read local Pi Agent state; it must not touch the CodexBar `pi-sessions` cache namespace used for Codex cost rollups.
- The parser must accept payloads with and without the new `pi` block so older payloads remain valid.
- The firmware UI should continue to render non-Pi providers exactly as before.
- The payload still crosses Upstash as a reduced, rolled-up contract; no raw session tree, command history, or per-message detail should appear in the published JSON.
- Pi local state is structured enough to be aggregated from session JSONL and model config, so no network call is required during host-side reduction.

## Performance Considerations
- Scanning `~/.pi/agent/sessions/` on each publish cycle should stay bounded by a small local file set; avoid per-message shelling out and prefer one pass per session file.
- The helper should prune to the last 30 days early so old session history does not dominate publish latency.
- Keep the publish path fail-soft and single-flight so a slow or malformed Pi helper does not block or duplicate the existing Upstash write.

## Migration Notes
No stored payload migration is required. If the Pi helper fails, the publisher can omit the `pi` block and continue publishing the existing provider payload unchanged.
