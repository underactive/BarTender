# Design: screen-lock

## Summary
Add a separate UI lock state that is entered by swipe-down and exited by swipe-up, without stopping stats ingestion or redraws. Idle screensaver entry is blocked while locked, and the UI renders a shared lock badge across provider pages and the summary screen.

## Requirements
- Lock is user-initiated from the touch gesture pipeline.
- Lock state is separate from `saver_active` and survives saver transitions.
- Locked UI keeps refreshing live stats and freshness text.
- Swipe-up unlocks and resumes the idle countdown immediately.
- Locked UI suppresses screensaver entry.
- Lock indicator appears on all screens.
- No payload, persistence, or asset changes.

## Current State Analysis
The UI already has a clean split: `ui.c` owns input policy and idle gating, `ui_screensaver.c` owns saver transitions, and `ui_render.c` owns all LVGL drawing. The research showed that saver entry is only polled in `ui_task()`, while input exit is handled in `ui_handle_input()`, so a separate lock bit can be inserted without disturbing touch classification or render cadence.

### Key Discoveries
- `firmware/main/ui_internal.h:136-172` already centralizes shared UI state, saver state, and nav state; this is the right place for a new lock bit.
- `firmware/main/ui.c:123-149` is the only idle-entry gate and can suppress saver entry while locked.
- `firmware/main/ui.c:251-309` is the sole gesture/nav state machine and already owns swipe-up/down behavior.
- `firmware/main/ui_screensaver.c:169-255` saves/restores nav state and can remain unchanged except for the lock gate.
- `firmware/main/ui_render.c:494-541` covers provider chrome, but `firmware/main/ui_render.c:1451-1560` is summary-specific, so the lock badge needs a shared helper.
- `firmware/main/touch.c:70-164` already emits swipe-down and swipe-up events; no new gesture event is required.

## Scope
### Building
- Add `st.locked` to shared UI state.
- Enter lock on swipe-down and exit on swipe-up in `ui_handle_input()`.
- Keep `last_input_ms` behavior so unlock restarts idle timing immediately.
- Block saver entry while locked, without suppressing renders or stats updates.
- Render a lock badge on provider pages and the summary screen through a shared helper.

### Not Building
- New gesture types or touch-driver changes.
- Persistent lock state across reboot.
- New icon assets or font changes.
- Payload/schema changes.
- Changes to provisioning mode behavior.

## Decisions
### 1) Separate lock bit from saver state
Use a dedicated `st.locked` boolean in shared UI state rather than reusing `saver_active` or saved-nav fields.

### 2) Gesture mapping
Swipe-down locks and swipe-up unlocks inside the `ui.c` nav/input state machine; touch remains semantic-event only.

### 3) Saver interaction
Idle saver entry is gated off while locked, but unlock does not alter render cadence or stats refresh behavior.

### 4) Lock badge rendering
Use one shared lock-badge helper in `ui_render.c` and call it from both provider chrome and the summary path.

## Desired End State
```c
// swipe down locks
ui_handle_input(&(app_evt_t){ .type = APP_EVT_SWIPE_DOWN });

// swipe up unlocks and idle timer resumes immediately
ui_handle_input(&(app_evt_t){ .type = APP_EVT_SWIPE_UP });

// stats keep updating while locked
ui_set_stats(&stats, fetched_ms);
```

- Add the lock bit before wiring gesture branches.
- Wire input handling before saver gating so unlock can still clear the idle timer.
- Add rendering last so the badge reflects the final state shape.
- Slice 1 must land before Slice 2 because rendering depends on the shared state field.

## Verification Notes
- Confirm swipe-down while unlocked sets lock without entering saver.
- Confirm swipe-up while locked clears lock and leaves nav state intact.
- Confirm idle timeout does not enter saver while locked.
- Confirm `ui_set_stats()` still triggers redraws while locked.
- Confirm provider pages and summary both show the same lock badge.

## Performance Considerations
- Lock checks are a single boolean in the existing UI loop; no measurable overhead expected.
- Rendering should reuse existing chrome/layout paths instead of adding new widgets per frame.

## Slices
### Slice 1: Lock state and gating

**Files**: `firmware/main/ui_internal.h`, `firmware/main/ui.c`, `firmware/main/ui_screensaver.c`

#### Automated Verification:
- [ ] `st.locked` exists in shared UI state: `bool locked;` is present in `firmware/main/ui_internal.h`.
- [ ] Idle saver entry is blocked while locked: `ui_task()` checks `!st.locked` before `saver_enter_locked(now)`.
- [ ] Swipe-down sets `st.locked = true` and does not fall through to summary paging.
- [ ] Swipe-up clears `st.locked = false` when locked and does not fall through to nav handling.
- [ ] `saver_enter_locked()` returns early while locked.

#### Manual Verification:
- [ ] Swipe-down locks the UI from summary and provider pages.
- [ ] Swipe-up unlocks and the next idle timeout is measured from that gesture.
- [ ] Stats continue updating while locked and the display still redraws.

### Slice 2: Shared lock badge

**Files**: `firmware/main/ui_render.c`

#### Automated Verification:
- [ ] `ui_render.c` owns one shared lock badge widget, created once and hidden by default.
- [ ] The lock badge is shown only when `st.locked` is true.
- [ ] Provider-page rendering calls the shared lock-badge helper.
- [ ] Summary rendering calls the shared lock-badge helper.
- [ ] Provisioning mode hides the lock badge.

#### Manual Verification:
- [ ] Locked provider pages show the same badge placement and styling as summary.
- [ ] Unlocking removes the badge immediately on the next render.
- [ ] No new asset or font dependency was introduced.
