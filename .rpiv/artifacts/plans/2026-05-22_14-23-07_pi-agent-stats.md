# Pi Agent stats Implementation Plan

## Overview

This plan implements the design for Pi Agent stats as a first-class provider in the existing v2 payload and device UI. The work stays within the current provider-row model: the host collects and reduces local Pi Agent state into a privacy-preserving `pi` block, the firmware parses that block without changing the overall navigation model, and the device renders Pi-specific spend/token/history labels inside the existing provider page chrome.

### Inherited Phase Structure

Inheriting 3 slices from `.rpiv/artifacts/designs/2026-05-22_14-16-27_pi-agent-stats.md` as 3 phases (1:1):

1. Host contract + publish merge — helper, publisher merge, schema, and parser/model updates (5 files)
2. Pi UI rendering — Cost-page rendering branch for Pi-specific labels and graph data (1 file)
3. Docs refresh — README, product specs, and integration docs sync (4 files)

Parallelism per design's Ordering Constraints: sequential. Phase 2 depends on Phase 1; Phase 3 depends on Phase 2; docs land last.
Total: 10 files across 3 phases. Success Criteria pass through from design's `## Slices` unchanged.

## Desired End State

The host can publish a payload that includes a Pi provider entry alongside existing providers:

```json
{
  "id": "pi",
  "ok": true,
  "p": 41.2,
  "pi": {
    "ps": 1245,
    "pt": 893421,
    "h": [91, 77, 124, 0, 0]
  }
}
```

On the device, the summary row still shows Pi in the same list as the other providers. Tapping Pi opens a Pi-branded Cost page that shows its max spend, max tokens, and 30-day graph, while the rest of the provider navigation continues to work exactly as it does today.

## What We're NOT Doing

- A new Pi-only screen or navigation path.
- Raw Pi session data or per-message detail on the device.
- Any change to Pi branding assets; those already exist.
- Any change to Upstash auth or the read/write token model.
- Any change to CodexBar’s existing provider collection logic.
- Any rewrite of the existing provider-row rendering model for non-Pi providers.

## Phase 1: Host contract + publish merge

### Overview

Add the local Pi Agent reduction helper, wire it into the publisher's fail-soft augmentation path, extend the payload contract, and teach the firmware data model/parser to accept the new optional `pi` block without breaking older payloads.

### Changes Required:

#### 1. Pi local stats helper
**File**: `scripts/pi-agent-stats.sh`
**Changes**: Add a standalone reducer that reads Pi Agent state from `~/.pi/agent/sessions/` and `~/.pi/agent/models.json`, aggregates the required rolled-up spend/token/history values, and emits only the reduced provider JSON object expected by the publisher.

#### 2. Publisher merge path
**File**: `scripts/codexbar-publish.sh`
**Changes**: Invoke the Pi helper during the existing local augmentation step, merge the returned `pi` block into the publish payload when present, and keep the current fail-soft behavior so missing or malformed Pi data never blanks the remote store.

#### 3. Payload contract
**File**: `docs/generated/codexbar-payload.schema.json`
**Changes**: Document the optional `pi` provider block in the v2 payload schema and keep the contract aligned with the reduced fields the helper publishes.

#### 4. Firmware provider model
**File**: `firmware/main/stats_model.h`
**Changes**: Reuse the existing provider fields for Pi's spend/token/history values so the model stays singular and the renderer can branch on provider id without forking a second field set.

#### 5. Firmware parser
**File**: `firmware/main/stats_model.c`
**Changes**: Map the optional `pi` block onto the existing provider model fields while preserving the permissive array-order parsing and keeping older payloads valid when the block is absent.

## Testing Strategy

### Automated:
- Build the firmware after the parser/model and UI changes: `cd firmware && idf.py build`.
- Exercise the publisher once with Pi data available and once with Pi data missing to confirm the publish path still succeeds and stays fail-soft.
- Verify the payload still parses when the optional `pi` block is absent.

### Manual Testing Steps:
1. Confirm the published payload includes a reduced Pi provider entry with spend, token, and 30-day history fields only.
2. On the device, verify Pi appears in the provider summary row and opens the Pi-branded Cost page.
3. Confirm non-Pi providers still render and navigate exactly as before.
4. Check the updated docs for the new provider and local Pi Agent source path.

## Performance Considerations

- Scanning `~/.pi/agent/sessions/` on each publish cycle should stay bounded by a small local file set; avoid per-message shelling out and prefer one pass per session file.
- The helper should prune to the last 30 days early so old session history does not dominate publish latency.
- Keep the publish path fail-soft and single-flight so a slow or malformed Pi helper does not block or duplicate the existing Upstash write.

## Migration Notes

No stored payload migration is required. If the Pi helper fails, the publisher can omit the `pi` block and continue publishing the existing provider payload unchanged.
