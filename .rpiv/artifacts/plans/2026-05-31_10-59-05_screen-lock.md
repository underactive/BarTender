# screen-lock Implementation Plan

## Overview
Implement a user-initiated screen lock for the ESP32 UI using the design in `.rpiv/artifacts/designs/2026-05-31_10-44-09_screen-lock.md`. The feature adds a separate lock bit, routes swipe-down/up through the existing UI gesture state machine, suppresses saver entry while locked, and renders a shared lock badge on provider pages and the summary screen.

## Desired End State
```c
// swipe down locks
ui_handle_input(&(app_evt_t){ .type = APP_EVT_SWIPE_DOWN });

// swipe up unlocks and idle timer resumes immediately
ui_handle_input(&(app_evt_t){ .type = APP_EVT_SWIPE_UP });

// stats keep updating while locked
ui_set_stats(&stats, fetched_ms);
```

## What We're NOT Doing
- New gesture types or touch-driver changes.
- Persistent lock state across reboot.
- New icon assets or font changes.
- Payload/schema changes.
- Changes to provisioning mode behavior.

## Phase 1: Lock state and gating

### Overview
Add the shared lock bit, route swipe-down/up through the UI state machine, and block saver entry while locked without affecting stats refresh or redraw cadence.

### Changes Required:

#### 1. Shared UI state
**File**: `firmware/main/ui_internal.h`
**Changes**: Add the lock bit to the shared UI state alongside saver/nav fields.

```c
    bool saver_active, saver_dim_only;
    bool locked;
    nav_level_t saved_nav_level;
```

#### 2. UI input and idle gate
**File**: `firmware/main/ui.c`
**Changes**: Gate idle saver entry on `!st.locked`, then handle swipe-down to lock and swipe-up to unlock in the existing nav/input state machine.

```c
            if (st.mode == UI_STATS && !st.saver_active && !st.locked && st.last_input_ms > 0 && now - st.last_input_ms >= SCREENSAVER_IDLE_MS) {
                saver_enter_locked(now);
                led_transition_enable();
            }
```

```c
    st.last_input_ms = esp_timer_get_time() / 1000;
    if (st.saver_active) { saver_exit_locked(st.last_input_ms); led_transition_disable(); r = UI_INPUT_CONSUMED; goto out; }

    if (st.locked) {
        if (ev->type == APP_EVT_SWIPE_UP) {
            st.locked = false;
            st.dirty = true;
        }
        goto out;
    }

    if (ev->type == APP_EVT_SWIPE_DOWN) {
        st.locked = true;
        st.dirty = true;
        goto out;
    }
```

#### 3. Saver entry guard
**File**: `firmware/main/ui_screensaver.c`
**Changes**: Keep saver mechanics isolated, but refuse saver entry while the UI is locked.

```c

{
    if (st.saver_active || st.mode != UI_STATS || st.locked) return;
```

## Phase 2: Shared lock badge

### Overview
Render one shared lock badge helper and call it from both provider chrome and the summary screen, while hiding it in provisioning mode.

### Changes Required:

#### 1. Shared badge widget and helper
**File**: `firmware/main/ui_render.c`
**Changes**: Add a shared lock badge widget, initialize it hidden, and expose a helper that shows/hides it based on `st.locked`.

```c

```

```c

    lv_obj_set_style_text_color(lock_badge, lv_color_hex(0xffffff), 0);
    lv_obj_set_style_text_font(lock_badge, &lv_font_montserrat_12, 0);
    lv_obj_set_style_pad_all(lock_badge, 0, 0);
    lv_obj_add_flag(lock_badge, LV_OBJ_FLAG_HIDDEN);
```

```c
static void render_lock_badge(bool locked, int x, int y)
{
    if (!lock_badge) return;
    if (!locked) {
        lv_obj_add_flag(lock_badge, LV_OBJ_FLAG_HIDDEN);
        return;
    }
    lv_label_set_text(lock_badge, "LOCKED");
    lv_obj_set_pos(lock_badge, x, y);
    lv_obj_clear_flag(lock_badge, LV_OBJ_FLAG_HIDDEN);
    lv_obj_move_foreground(lock_badge);
}
```

## Testing Strategy

### Automated:
- Build the firmware and confirm the modified UI files compile together.
- Use the existing UI/test path to validate lock state transitions and render updates.

### Manual Testing Steps:
1. Swipe down from summary and provider pages; confirm the UI locks and saver entry is suppressed.
2. Swipe up while locked; confirm the UI unlocks and the idle countdown restarts immediately.
3. Leave the UI idle while locked and confirm saver entry does not occur.
4. Verify provider pages and summary both show the lock badge.

## Performance Considerations
- Lock checks are a single boolean in the existing UI loop; no measurable overhead expected.
- Rendering should reuse existing chrome/layout paths instead of adding new widgets per frame.
